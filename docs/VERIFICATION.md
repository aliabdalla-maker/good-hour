# What is verified, and how

This document exists because "implemented" and "working" were being used
interchangeably, and they are not the same claim. Every row below says which of
the two applies.

## The three levels of evidence

| Level | Means | Worth |
|---|---|---|
| **Tested** | An automated assertion fails if it breaks | Strong, and only as wide as the assertion |
| **Exercised** | Real users/data have run through it in production | Strong, and narrow to what was actually run |
| **Written** | The code exists and typechecks | Weak — this is the level most features sit at |

**The honest summary:** the auction engine and the products-and-services
marketplace are code-complete and unit-tested but have never executed a single
real bid or order. Correctness claims about them are claims about code.

## Rules that produced this document

Each of these is a response to a specific failure, not general good practice.

### 1. A probe for "is this hole closed?" must never take the action the hole permits

To check whether the ADMIN self-registration fix had deployed, a loop polled
`POST /auth/register` with `role: "ADMIN"` and waited for 201 to become 400. Four
polls succeeded first. That created **four real ADMIN accounts with a known
password on the production database**, live for about eight minutes. They were
found by noticing a user count of 8 against an expected 4 — not by any check that
had been designed.

Use `GET /health`, which now returns the commit SHA the process was built from.
Comparing that against the deployed commit answers the same question and cannot
change state.

### 2. A checker that has never gone red is unmeasured, not passing

Three verifiers reported green while being incapable of detecting the thing they
were for:

- one grepped page HTML for `NEXT_PUBLIC_API_URL`, which Next.js inlines into a
  JS chunk — so "still the old build" was noise for an entire debugging session;
- a diagram validator checked only the first line, and passed PlantUML syntax
  sitting inside a `classDiagram`;
- a money test compared floats by subtraction (`80.8 - 80 !== 0.8`).

Every check in `contrast.test.ts` and `designAudit.test.ts` is therefore paired
with a fixture it **must** flag: a banded ramp, a sub-AA `600`, a
`hover:bg-brand-600` on a `bg-brand-600`, an empty parse. `designAudit.test.ts`
also asserts the file walk found >40 files, because two of its checks would
otherwise pass vacuously on an empty scan.

### 3. Published numbers are generated, not typed

The design-token contrast table was hand-typed and nine of twelve figures were
wrong in the second decimal — computed with the 0.03928 sRGB erratum rather than
the normative 0.04045. Wrong by too little to change any pass/fail verdict, and
therefore invisible to review indefinitely.

`docs/DESIGN_TOKENS.md` is now generated by `npm run docs:tokens`, and a stale
copy fails the test suite.

### 4. Invariants are asserted, not argued

The credit-redemption arbitrage (37.5%) shipped *with a code comment defending
the design*. A confabulated rationale is worse than a silent bug: it inoculates
the next reader against noticing. The cap now lives in
`packages/shared/src/redemption.ts` with a test that sweeps hours × rate × unit
value and asserts the bound directly.

### 5. Logic only reachable through the database gets extracted

The first proxy-bidding implementation looped "everyone counters by one
increment" up to a round cap. With £0.50 increments against ceilings of £70 and
£62 it stopped around £58 with the **£62 mandate in front** — the iteration limit
was choosing the winner. It carried a comment describing it as proxy bidding:
right vocabulary, different algorithm.

It was untestable because it lived inside a Prisma call chain. The decision is now
`resolveProxyContest` in `packages/shared`, and `proxyContest.test.ts` sweeps the
ceiling gap from £0.50 to £40.

## Gate

```bash
npm run lint && npm run typecheck && npm test
```

94 unit tests at the time of writing.

## Integration gate

```bash
DATABASE_URL=postgresql://... npm run test:integration
```

7 tests against a real Postgres, covering what no unit test can reach: oversell
under 8 concurrent buyers on 1 unit of stock, 10 concurrent wallet spends, the
read-then-write gap, index-enforced idempotency on a duplicated top-up, and the
outbox relay.

**This suite had never actually run.** `npm run test:integration` loaded `.env`
via `-r dotenv/config`, but `node --test` spawns each file in a *child* process
and a CJS `--require` does not carry across — so `DATABASE_URL` was absent in the
child and the run hung with no output rather than failing. Two pre-existing
`.itest.ts` files had therefore never executed. `scripts/run-itest.mjs` now loads
`.env` and passes the resolved environment to the children, and exits with a
readable message when `DATABASE_URL` is missing instead of hanging.

It found a real defect on its first successful run: ten concurrent £20 spends
against a £100 balance had only **two** succeed. The other three affordable ones
were rejected with a serialisation conflict — safe, but a user with money was
told to try again because someone else transacted at the same moment. P2034 is
precisely the error Postgres raises to mean "retry me", so `applyWalletWrites`
now retries up to three times with jittered backoff. Idempotency is
index-enforced, so a retry can never double-apply.
